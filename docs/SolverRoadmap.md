# 后续机制与求解器展望

这是对 `idea.md` 的设计分析，不是已支持语法清单。目前仅实现计数与直接字母比较；第三章落地了设想 1。继续以“一种机制、一组例题、独立验证”为单位推进。玩家界面只显示符号与题目，规则解释留在开发文档。

## 类型与共同约束

后续 AST 应明确区分数值、答案字母、题号三类结果。答案字母 A 与题号 (1) 即使能对应某种序号，也不能自动当成数字参与算术。建议把约束拆成左表达式、比较运算符、右表达式：右表达式来自所选选项的内容。现阶段 `count` 与 `answer` 已明确区分数量与字母，后续扩展仍沿用 AST 求值，渲染层单独负责符号。

所有引用都在同一个完整候选答案下解释，不按题号顺序逐题定答案。`ref(n)` 返回第 n 题的答案标签；未来的 `*(n)` 才返回其所选选项的内容。`@solution` 始终声明完整的 A–E 答案串，不建议改成 `@solution ref(1)`，否则容易混淆求值表达式和作者声明。

## 逐项展望

| 设想 | AST/语义方向 | 需要先确定的边界 | 性能机会 |
| --- | --- | --- | --- |
| 1. 直接选项 | 已支持 `answer(literalOption/ref/self)` 与字母内容 | 标签与内容要区分；本次第三章全部唯一解 | 很多约束只依赖一两道题，可提前排除候选 |
| 2. 大于小于 | 独立的 `eq`、`lt`、`gt` 比较节点 | 明确 `prompt >` 是左边大于右边；字母次序定义为 A<B<C<D<E；禁止数量与字母混比 | 数值区间、字母可行集合可用于剪枝 |
| 3. 选项引用 | 选项从字面值扩展为同类型表达式，如 `ref(n)` | 两边引用返回标签；题号字面值 `(n)` 与标签引用 `ref(n)` 是两种东西；检查越界 | 建立依赖图，变量齐备时立即验证局部约束 |
| 4. 次序 | `nthAnswer(labelExpr, index)` 返回题号；正索引从头，负索引从尾 | 没有第 k 个匹配时如何处理？建议“未定义导致该约束不满足”；约定 #1、#-1 的 token 边界 | 维护前缀/后缀数量与未赋值位置范围 |
| 5. 指针 | `selectedValue(questionExpr)` 读取所选内容 | 目标必须是有效题号；解引用后的值类型需确定；自指内容表达式可能形成环 | 候选内记忆化；使用访问栈检测循环 |
| 6. 多重/无穷指针 | 显式解引用深度，或沿题号链接追踪到终点/循环 | 无限跟随用 visited 集合判环，不能真的递归到无限；循环不应默默视为正确 | 有限图遍历、候选内缓存；必要时用强连通分量分析 |
| 7. 非 | `not(constraint)`，作用于整个比较结果 | 规定括号与作用范围；`?` 和未定义不能简单被 ! 翻成真 | 利用被否定关系排除候选 |
| 8. 运算 | 数值表达式树与明确优先级；渲染乘除为 × ÷ | 是否允许负数、分数、整除？除零怎么处理？建议先落地整数加减，再讨论乘除 | 常量折叠、值域界限、区间传播 |

无限指针是需要单独设计的机制。你的设想允许某道题主要用于构造循环和约束其他题，但这不能由一般的“求值失败”自动得到。建议将“必须处于循环”明确建模为可验证的约束，求值结果区分普通值、循环、未定义。循环结果是否免除内容比较，需要由该机制明确规定，不能让所有错误引用都变成无约束题。

反例（无解/多解例题）也应显式标记为专用展示类型，如未来的 `@expect none` / `multiple`。它需要独立的验证与界面反馈，不能放宽普通已发布题目的唯一解要求。该语法目前未实现。

## 性能演进

当前求解器枚举每个小题的五种答案，共有 `5^n` 个完整候选；它保留全部解。现有最多六小题的题组和第三章适合继续用它做正确性基准。机制越复杂，每次候选求值的成本也可能增加，不能只看小题数量。

建议按以下顺序改进，而不立即更换求解器：

1. **先记录成本。** 对新机制记录候选数、耗时、解数量，保留当前枚举器作为小题组的对照实现。
2. **提早检查局部约束。** 给每个表达式计算依赖；字母约束的相关变量一旦赋值就能判断。计数约束要用已出现数量与未赋值数量形成上下界，不能因当前数量尚不等于目标值而错误剪枝。
3. **缩小变量取值域。** 先过滤不可能的自引用/常量选项，再传播约束；优先选择候选最少、关联最多的题目进行搜索。输出答案仍按原始题号排序。
4. **分开诊断与发布检查。** CLI 的“展示全部解”保留完整枚举；唯一性验证可在找到第二个解后停止，但必须用明确的 `multiple` 或“至少 2”结果，不能把截断结果伪称精确总数。
5. **把重计算移出首屏。** 更复杂的题可以在构建阶段从同一 DSL 生成已验证结果，或在 Web Worker 中求解，避免页面主线程阻塞。生成文件不作为手工维护的答案表；每次构建独立验证 DSL 与声明。Worker 只改善响应性，本身不会降低搜索复杂度。
6. **再考虑专门求解技术。** 若约束传播仍不够，评估 CSP/SAT 编码。计数和离散关系较适合编码；动态指针、循环和算术需要先有精确语义。届时再做技术选型与基准。

每次优化都应在原枚举器可承受的小题组上比较完整解集合，覆盖无解、唯一解、多解、自指与循环；还应覆盖五个 `?` 的小题，因为它自身没有等式约束但会改变别题的计数。

下一步可优先实现“大于小于”，或先实现“选项引用”。前者需要定下字母排序与左右方向，后者需要扩展选项表达式类型；两者都比指针更容易定义与验证。暂不一次性实现整份设想。
